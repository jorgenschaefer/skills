# Evidence: kh-finder, 2026-11-06 to 2026-11-07

What we saw when using the skills on an existing project. Each observation
says what happened, where to look, and why, as far as the sessions show.

## The project and the sessions

`~/Projects/kh-finder` is a small offline web app that already existed. It
lists hospitals for an emergency, by specialty and distance. One change ran
through the whole new workflow: ordering the list by driving time from a
paid outside API. A second, small change made that API work on the local
dev server.

## Observations

### 1. The agent recommends the heavier option, and the developer cuts it back

Seen in five sessions, about ten times. The agent proposed a five-phase
rewrite, a server-side proxy with a PIN per person and rate limiting
(`c7547d4c`), the bigger of three approaches (`2e97ef0c`), and a rule based on
distance and time when time alone was enough (`6878405c`, `dc1e029c`). In
`723ff5f4` it first recommended a small server written by hand, then a
globally installed web server. Only after two objections did it reach a
dev-only package with eight lines of config.

The developer's words: "Simplificty first", "maybe I'm overengineering now",
"Only time… I'm looking NOW", „Schon wieder was selbst bauen. Davon will ich
weniger, nicht mehr", „Keine globalen Installationen".

Why: the cases in `723ff5f4` have their own cause. The project's `CLAUDE.md`
still said "nothing it ships has a dependency", although the developer had
just said this rule was dropped, and the agent followed the old rule. The
other cases are not about dependencies. They are more scope than the problem
needed, although `understand-change` says to put the simplest approach
first. Why that did not hold, the sessions do not show.

### 2. Reports list fixes and successes, although the skills forbid it

Seen in five reports: both `accept-change` reports in `6878405c` and
`dc1e029c`, and the `build-change` report in `68ef4750` ("The review found two
problems in the new dev server, and both are fixed"). One case may be a fair
exception: a fixed bug that broke a decision that matters, such as a race
with the user's consent.

### 3. `backlog` writes sizes without asking when another flow uses it

In `68ef4750`, `backlog` was used twice from inside other work: once after a
question during the build, once from `accept-change`. Both times the agent
wrote and committed the item with sizes it chose, then said: "I set the sizes
… myself; you haven't confirmed them yet". When the developer started
`/backlog` directly (`723ff5f4`, end of `68ef4750`), it proposed the sizes
first, as the skill says.

### 4. The review and the user stand-in find bugs the build missed

Seen again. In `6878405c` and `dc1e029c`: a timer that stalled while the phone
slept, a hospital the API left out that silently dropped from the list, and a
race between withdrawing consent and a request in flight. In `68ef4750`: under
the dev server, the service worker cached a stylesheet as JavaScript, and any
page on another localhost port could read the API key. The stand-in also
found usability problems the reviewer did not. This adds to observations 8
and 10 of the workout logbook.

### 5. Secrets and paid outside calls were not designed

In `2e97ef0c`, `design-change` never asked where the API key lives during
development, so the agent asked for the key in the chat, and it ended up in
shell commands and in the transcript. Nobody asked how often a paid call
fires: re-sorting every 100 m sent 28 requests on a 3 km drive (`6878405c`).
Nobody asked what happens to a request already on its way when consent is
withdrawn. This adds to observations 11 and 13 of the workout logbook.

### 6. `accept-change` did not close its loop after a redesign

In `6878405c` the agent rebuilt the feature twice inside the accept session.
After the second rebuild no review ran, and the stand-in never tried the new
button. The developer had to start `/review-change` and `/accept-change`
again by hand (`fc97bed3`, `dc1e029c`).

### 7. `understand-change` did not start on an open request

In `c7547d4c` the developer wrote, in effect, "question every assumption and
write a roadmap". The skill did not start. The agent agreed with the premise,
used `nextjs-project-setup` as a guide to the developer's stack, and put a
feeling, a migration and a feature into one change file. Once the skill ran,
asking what prompted the request found the real problem.

### 8. The user stand-in cannot resize the window

In `dc1e029c` the stand-in could not resize the browser and checked phone
width in a 360 px frame instead. In `68ef4750` it did not find that
workaround, and the report says: "Nobody tried the change at phone width."
For an app used on phones, that leaves the most important width untested.

### 9. A `learn-from-sessions` run that ends early loses its work

`b4d1e1ab` read 11 sessions with four subagents, reported, and asked the
developer what to apply. No answer came, so nothing was written down and no
session was marked as read. The next run had to read the same sessions
again.

### 10. Smaller ones

- The first mock-up showed the options without the real page around them
  (`2e97ef0c`).
- The chat summary must name every decision, because the developer does not
  read the change file. One summary left out "the app asks the API by
  itself" (`2e97ef0c`).
- A report that says what nobody could try should also say how to try it.
  The developer had to ask how to test with the real key (`dc1e029c`).
- Some questions are cheap to undo but need the developer's knowledge of the
  domain, and they were worth asking (`6878405c`).

## What worked

- **Stopping before the build holds.** After the fix of 2026-11-06, in
  `723ff5f4`, `design-change` ended with "start the build in a fresh session".
  Before the fix, in `2e97ef0c`, it had gone straight on to the build, and the
  builder had started `accept-change` itself.
- **`accept-change` checked what holds each decision, and it found a gap.** A
  test named in the change file did not pin the decision, so it added one.
  It also noticed three findings the developer had never answered, and asked
  about them before deleting the change file (`68ef4750`).
- **Claims were checked by running things.** When the developer disputed a
  claim about `localhost`, the agent sent one real request for each case,
  and the API's answers settled it (`723ff5f4`). The reviewer started the
  real web server config in a throwaway container. The stand-in faked the
  API's documented answer (`dc1e029c`).
- **The builder broke its own code on purpose** to check that the new tests
  fail on the old code (`6878405c`).
- **Research into the API's terms shaped three decisions**, such as not
  caching its results (`2e97ef0c`).
- **Untracked secret files were raised as a question**, not committed.
- **"How did you notice?" found the real problem** once `understand-change`
  ran (`c7547d4c`).
- **Explaining the code from scratch, then checking the explanation against
  the code, found a filter bug** that the tests miss (`2a5ba9df`).

## What this suggests

Not yet agreed. For discussion.

- **The agent recommends more scope than the problem needs**, despite
  "simplest first" (1). The cause is not clear yet.
- **A project rule the developer drops in the session must give way to what
  they said**, and `CLAUDE.md` should change with it (1).
- **The report rule against listing fixes does not hold** (2). Either the
  rule goes, or the skills say why it is there and name the exception.
- **`backlog` must ask for sizes whoever calls it** (3).
- **`design-change` should ask about secrets in development, and about how
  often a paid call fires** (5).
- **`accept-change` needs a rule for a redesign inside the accept session:**
  go back to `build-change`, or run the review and the stand-in again (6).
- **`try-change` should know the frame workaround for phone width**, or say
  plainly that it could not check it (8).
- **`learn-from-sessions` should write its findings to a file before it asks
  the developer anything** (9).
